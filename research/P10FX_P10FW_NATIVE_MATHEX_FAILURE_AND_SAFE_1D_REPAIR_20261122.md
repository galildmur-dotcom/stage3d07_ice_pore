# Stage3D07 — P10FX: остановка P10FW/M1U и безопасное исправление MathEx

**Дата:** 2026-11-22. **Статус:** `P10FW_M1U_STOP_NO_FEM` →
`P10FX_SOURCE_ONLY_PACKAGE_PASS_NATIVE_WINDOWS_PENDING`. Физический GO **не выдан**.

## Первичное свидетельство

Пользователь передал `P10FW_M1U_MESH_EVIDENCE.zip`, SHA256
`9a06e236b53dcaa712f48d863d7bc53b939307ed7f6b17a4d5307e1fb3c485de`.
Структура ZIP, 8/8 CRC: PASS. Содержимое конфиденциального пользовательского
архива не копируется в публичный репозиторий; приведены только проверяемые
диагностические сведения и криптографические дайджесты.

`P10FW_M1U_MANIFEST.json` и `P10FW_GMSH_3D_LOG.txt`:

| Показатель | Наблюдение |
| --- | --- |
| Native Gmsh | 4.15.2, `-3 -nt 2`, exit `1` |
| Время, пик памяти | 3.008 s, 253,878,272 B |
| Первая ошибка | `Error [mathex::parse()]: Invalid expression` при `Meshing 1D` |
| Конкретный дефект | `((z-0.03)/sqrt(...))--0.80000000000000004` в `Field[5]` |
| Каскад | `Field 5: invalid matheval expression`, invalid spherical surface 7/8, `HXT 3D mesh failed` |
| Выходная M1U | 0 Tet10, нет валидного 3D объёма |
| FEM attempts | 0 |

Первичная причина — сериализация математически верного выражения
`mu - (-0.8)` в виде `mu--0.8`; Python такую запись вычисляет, но
парсер MathEx Gmsh 4.15.2 отвергает. `-parse_and_exit` и 6018
проверок через Python ошибку **не выявили**, потому что MathEx
компилируется лишь при реальном обращении к полю во время построения
1D. Это дефект программы P10FW, а не нехватка ОЗУ и не доказательство
геометрической непригодности сферической поры.

Одноразовый `-3` для P10FW использован: повторное исполнение P10FW
**запрещено**. Ремонт выпускается как новая ветка выполнения P10FX,
кандидат `M1V_CANDIDATE` с отдельным marker и отдельным именем;
оригиналы `M0.msh/M0.geo/M1.msh/M1.geo` сохраняются побайтово.

## Ремонт и воспроизводимость

В `P10FX_uniform_math.py` отрицательные угловые узлы интерполяции
записываются как `mu + abs(knot)` и операторы `--`, `+-`, `++`, `-+`
запрещены в полных выражениях MathEval до вызова Gmsh.

`python3 scripts/p10fx_verify_mathex_sign_repair.py`:

- 6018 точек сравнения оригинального P10FW с P10FX: `PASS`.
- Макс. относительная разница предписанного поля `h` и `logcomp`: **0.0**.
- Длина Field5 7781 → 7754 символов; калибровка и гладкое C¹ поле
  физически и математически **не меняются**.
- Цель остаётся фактическим `Veff(M1V)/Veff(M0) ∈ [0.80, 0.85]`
  в *каждой* из 18 подписанных 3D зон, не только в среднем.
- Это компенсация нелинейного смещения Gmsh при равномерном требовании
  объёма; никакая физическая адаптивная `κ(x)` пока не вычислялась.

В новой `01_P10FX_SAFE_PREFLIGHT_ONLY.cmd` выполняются проверки SHA,
наследования M0, формульной эквивалентности, `-parse_and_exit` **и
отдельное нативное `gmsh -1`** на временной копии `.geo`. Такая 1D
проверка вызывает именно MathEx, который P10FW не проверял. Лог 1D
сохраняется и SHA-прикрепляется к доказательству preflight.
Условие запуска `02` включает успешный native exit0, наличие настоящего
1D файла, строку `Done meshing 1D` и отсутствие `Error`; при любом
отклонении `02` запрещён, новый one-shot 3D не расходуется.

Новая программа `02_P10FX_ONE_M1V_3D_ONLY.cmd`: один `gmsh -3`, максимум
900 s/8 GiB/2 GiB, 27QP геометрический аудит, **0 FEM**, без ручного
ввода, окно остаётся открытым, уникальные постоянные one-shot маркеры
создаются перед 3D. Созданный 3D mesh — *только кандидат*, до
независимой проверки curved343/729QP по всему объёму научный GO закрыт.

## Следующий научный переход

1. На Windows распаковать P10FX в **новую папку** и запустить `01`.
2. Если 1D `P10FX_PREFLIGHT_PASS`, единожды запустить `02`.
3. Передать `P10FX_M1V_MESH_EVIDENCE.zip`.
4. Независимо проверить геометрию Tet10 и 343/729QP для 18 зон.
   Если **все** отношения ∈ [0.80,0.85] — только тогда обсуждать GO
   для свежих forward/adjoint FEM. При одном провале STOP и новая
   отдельная научно обоснованная итерация, без повторов one-shot.
