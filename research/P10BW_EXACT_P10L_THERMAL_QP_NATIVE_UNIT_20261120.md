## 2. Что реализовано и с какой математикой

`stage3d10bw_thermal_qp_partition.hpp` — header-only диагностический модуль **после** включения `geometry_stage3d01.cpp` (`STAGE3D01_LIBRARY`) и `stage3d10l_thermal_adjoint.hpp`, namespace `ice3d::p10bw`.

Для одного обратного временного шага на **той же** базовой сетке он принимает `velocity`, `psi_n`, `theta_n`, `theta_{n−1}`, `dt`, `ambient_n`. Программа **не решает** прямую или сопряжённую задачу, не меняет матрицы P10L, `psi` и `theta`. Вместо этого она воспроизводит те же геометрические JVP P10L **на каждом Gauss QP до матричной свёртки**:

\[
\begin{aligned}
d_{M,e,q,n}&=\rho c_p\,dw\,\psi_q\,(\theta_n-\theta_{n-1})_q,\\
d_{K,e,q,n}&=\Delta t\,k\left[dw\,\nabla\psi\cdot\nabla\theta_n+w\left(\delta\nabla\psi\cdot\nabla\theta_n+\nabla\psi\cdot\delta\nabla\theta_n\right)\right],\\
d_{R,f,q,n}&=\Delta t\,h\,dA\,\psi_q(\theta_{n,q}-\theta_{\infty,n}).
\end{aligned}
\]

Здесь `w=q.w detJ`, `dw=q.w ddetJ`, $δ\nabla N$ полностью берётся из аналитической производной криволинейного отображения; на верхней Tri6-грани Robin stiffness и Robin load объединены **ровно один раз**. Весь `K'` имеет собственную объемную часть и поверхностную Robin часть, которая **не исчезает по определению**. Итог:

\[
\sum_{e,q}(d_M+d_K)+\sum_{f,q}d_R
=\psi_n^{\mathsf T}[M'(\theta_n-\theta_{n-1})+
\Delta t K'\theta_n-\Delta t b'\theta_{\infty,n}].
\]

Две меры локализации сразу регистрируются без хранения всей QP-истории: (а) 10 радиальных физических интервалов P10S `[0,.02,.05,.1,.25,.5,1,2,5,15]` мм от стенки; (б) 10 полярных полос по \(\mu=\cos\vartheta\), с выбором по **физической координате Gauss QP**, не по номеру механического QP. `Snapshot.cells[100]` хранит `mass/diffusion`, `thermal_qp_count`, `volume_m3`, интеграл отклонения температуры `theta_integral`; верхняя Tri6-грань и её `robin`, площадь и QP count — отдельно. `total()` суммирует **все** ячейки + Robin. Нет записи миллионов строк, нет сохранения `psi_n` после текущего шага. Тепловая квадратура — **64 QP/Tet10**, верхняя — **16 QP/Tri6**; механическая 27 QP/Tet10 **не подставляется**.

Зональная плотность зависит от принятого **объёмного продолжения скорости формы**, не является автоматически уникальным граничным форм-градиентом. Числовые компоненты output unit относятся только к синтетической сетке/полям, **не к механике пресноводного льда**.

## 3. Проверки и фактические результаты

Нативный C++ тест `P10BW_thermal_qp_native_unit.cpp` действительно включает два точных исходника P10L/геометрии по pinned SHA. Локально выполнено:

```bash
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic \
  -I pinned -I proposal \
  proposal/P10BW_thermal_qp_native_unit.cpp -o P10BW_thermal_qp_native_unit
./P10BW_thermal_qp_native_unit
```

Рабочая директория в приведённом примере — локальный `p10bw_workspace/`, а `pinned/` содержит лишь прочитанные первоисточники (не публикуются вторично). Среда проверки: Linux, **g++ 14.2.0**, C++20. **Никакая Windows GNU13.1 MinGW Release сборка этого нового заголовка пока не проводилась**.

Тест — **синтетическая** геометрия из **двух криволинейных Tet10, имеющих общую грань**, и **одной удалённой отдельной Tri6 Robin**; 20 узлов, 2×64=128 объёмных QP + 16 поверхностных QP. Тестовые `psi`, `theta`, `theta_prev` — заданные гладкие/осциллирующие узловые массивы, а не найденная механическая или тепловая история. Три реальных направления полей скорости `R`, `tz`, `y20` повторяют P10V cutoff 5 мм на базовых координатах; отдельное **синтетическое** `top` заставляет Robin face деформироваться, чтобы независимо проверить знак и нагрузку.

## 4. Почему это ещё не готовый производственный FEM-экспорт

- В реальном P10P `psi_n` создаётся внутри цикла `obs,n` после `H::solve`. Для нового рекордера нужно **опционально** вызывать `contract_step(...)` до разрушения `psi_n` и **только для `obs==jpeak`**, чтобы избежать трёхкратного объёма диагностики. Сейчас это **не подключено** к `stage3d10p_partial_audit.cpp` и штатным CMake target.
- Для каждого реального шага следует независимо вычислять глобальный уже существующий контракт через CSR и требовать `Σ_{bins,face}≈thermal_step_global`; после всех шагов — то же для штатного `thermal_adjoint_per_m` в **том же run**, не против исторического неизвестного EXE. Для почти полной знаковой компенсации абсолютную и относительную невязки оценивать совместно.
- Нужно добавить **отдельную** диагностическую цель, собственный `RUN_MANIFEST.json`, точный исходный и EXE SHA, toolchain/configure/build/native exit; затем короткий native unit/preflight в Windows GNU13.1 MinGW. Проверка 7/7 на Linux **не устанавливает** правильность компиляции с Windows Qt Creator, работу EDV или `P10W` на настоящих сетках.
- Уже построенный `H::assemble` вычисляет пространственные матрицы один раз; `contract_step` дополнительно проходит **64 QP каждого Tet10 для каждого выбранного шага**. `Snapshot` потоковый (`100` ячеек), но CPU время не нулевое. Не назначать H2/36 или H4 автоматически; точную оценку времени/ОЗУ нового H0 рассчитывать после preflight и фактической конфигурации.
- Вынос тепловой shape-производной на оболочки для объемной скорости не равен уникальному граничному форм-градиенту и не служит доказательством полярного механизма или пространственной сходимости `D_R jpeak`.
