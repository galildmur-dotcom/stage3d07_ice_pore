## Независимый контроль GitHub

Через подключение GitHub выполнены читающие проверки 19.11.2026:

- поиск ветки `research/p10bi-local-seven-sources-20261119` вернул **пустой список**; в GitHub уже есть отдельный P10BG-кандидат `research/p10bg-source-integration-20261119`;
- запрос к GitHub API для родительского коммита `c0498f6dc98628b62eff996a76844297c7a35094` вернул `422 No commit found for SHA`.

Следовательно, **прямой `git push` локальной ветки нельзя считать отправкой только семи файлов**. Для публикации SHA `90fd2559…` Git обычно должен также передать недостающую цепочку родительских коммитов и её Git-объекты; она может содержать старые крупные или конфиденциальные файлы. Отдельная ветка защитила бы существующий GitHub `master` от перезаписи, **но не исключила бы передачу истории**. До оценки состава истории и согласия исследователя `push` не выполнялся.

## Следующий безопасный шаг — P10BL

Подготовлен `tools/P10BL_HISTORY_SCOPE_ONECLICK_20261119.zip`, инструкция `tools/P10BL_HISTORY_SCOPE_20261119/README_RU.md`. Программа **только читает локальный Git**, считает число достижимых коммитов/объектов, количество и суммарный несжатый размер blob, крупнейший blob, верхнеуровневые группы путей и число имён с потенциально чувствительными шаблонами. Имена конкретных исторических файлов, содержимое, токены, ветки и remote не экспортирует и не меняет. Ни одной сетевой операции, push/fetch/pull, FEM.

Ожидается **один `P10BL_HISTORY_SCOPE.txt`**. После него решать совместно: разрешён ли перенос всего достижимого исторического дерева как новой ветки GitHub или лучше ограничиться отдельно отмеченным проверенным снимком семи исходников (архивный P10BF и кандидат P10BG уже присутствуют на GitHub) с документированной ссылкой на локальный SHA. Исходные P10BB/P10BE, выводы о полной производной и недоказанной пространственной сходимости не меняются.
