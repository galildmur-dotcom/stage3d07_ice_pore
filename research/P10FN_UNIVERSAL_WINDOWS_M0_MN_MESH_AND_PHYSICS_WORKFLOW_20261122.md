# P10FN — универсальные Windows-программы сеток и физики для M0…MN

**Статус `SOURCE_BUNDLE_BUILT_AND_SELFTEST_PASS; WINDOWS_NATIVE_GMSH_PENDING`.**
Публикуется автономный пакет P10FN, который отделяет генерацию M(n+1)
от физического расчёта на уже одобренной сетке. Полный порядок
исследователя: **генерация → evidence → независимый geometry GO → физика
→ evidence → межсеточный signed4D анализ → новый рецепт κ и M(n+1)**.

## Основные решения

1. Постоянные пути Windows: `G:\ildar\Stage3D07\meshes\M0.msh,...,MN.msh`
   и `G:\ildar\Stage3D07\LOCAL_RUNS\P10FN_*`.
2. Две кнопки: `01_GENERATE_NEXT_MESH.cmd` и
   `02_PHYSICS_LATEST_APPROVED_R.cmd`; дополнительно точные M0/M1/M2
   и направления tz/y20. Никаких `input()`, подтверждающих фраз,
   ручного PowerShell/Git Bash или восстановления старого H0 cache.
3. Точная исходная P10EY M2 геометрия и физические теги наследуются
   через Gmsh `Include`, а последующая C¹-адаптация определяется рекурсией
   `h_{n+1} = h_n (1−α κ_n)^(1/3)`.
   Здесь `κ_n(x)∈[0,1]` — аналитическое C¹ произведение гладких
   радиального и полярного окон; `0.15≤α≤0.25`. Рекурсия нацелена
   на изменение **характерного локального объёма**, не на абсолютный
   глобальный Tet10 count. Внутри κ0-полей target h сохраняется,
   не утверждается точное сохранение объёма отдельных элементов Gmsh.
4. Первичный M3-рецепт после P10FM: север κ=1 при 0–50 μм и |μ|≥0.8;
   юг κ=0.8; плавный спад к нулю по 50–350 μм и |μ| 0.8→0.55.
   Номинально target V_M3/V_M2 =0.80 на севере, 0.84 на юге,
   1 вне области κ. Данные φ использованы в диагностике, не
   навязаны как скачкообразный множитель поля размера.
5. До запуска физики требуется `approvals/Mk.json` с mesh SHA-256,
   указанным после независимой геометрической проверки. M0/M1/M2
   предварительно известны и утверждены по предыдущим физическим данным;
   никакого автоматического одобрения новых MN после встроенного QA.
6. Физический код — тот же P10DL/P10W производственный аналитический
   Tet10 транзиентный adjoint, включён из оригинальных pinned source,
   только бинарная оболочка теперь принимает `M[0-9]+.msh` и режимы
   R/tz/y20, защищая точный профиль 6×150, ξ=0, EDV_VAR, cutoff5мм.
   После каждого полного запуска независимый универсальный аудитор
   проверяет 7206 signed4D строк, QP-count и глобальную/покомпонентную
   closure против физических P10W CSV. 18 механических adjoint решений
   для 3 функционалов; никаких production geometry FD.
7. Одноразовые маркеры по SHA родительской сетки/новой сетке и по
   физическому SHA+моде+EXE создаются **до** нативного процесса;
   Windows Job Object жёстко ограничивает память/убивает процесс
   при закрытии. Генерация: 900 с/8 GiB; физика: 21600 с/40 GiB
   (не превышая доступную RAM−8 GiB); Gmsh и физика не повторяются
   автоматически и не перезаписывают файлы.
8. Все доказательные ZIP передаются приватно исследователем. Публичная
   ветка содержит только инструментарий/рецепты, а не raw исторические MSH.

## Проверки текущего релиза

- `P10FN_BUNDLE_SOURCE_AND_RECIPE_CHECK_OK`: 115 ZIP файлов,
  SHA-inventory, M3-рецепт, схемы одобрений.
- `P10FN_ADAPT_SOURCE_SELFTEST_OK`: полярные/радиальные C¹-базисы,
  κ(север)=1, κ(юг)=0.8, κ(экватор)=0, запрещённые скачки нумерации.
- Независимый Python аудит **реальной оригинальной M2**: 14723 узла,
  10094 Tet10, 194 pore Tri6, 272538 QP, не положительных detJ **0**,
  native M2 SHA совпал.
- Новый универсальный анализ соседних curved-объёмов точно воспроизвёл
  ранее опубликованные P10FH значения: 419 приполюсных соседних граней,
  q>1.25 для 95, median 1.13347094, p95 1.42574446, p99 1.82774111;
  по всему M2 19541 внутренних граней, median 1.10076062,
  p95 1.36876327. Это проверка алгоритмической преемственности.
- `P10FN_ANY_MESH_GUARD_SELFTEST_OK`: Linux g++14.2 сборка и
  встроенный production dependency/4D-bin/guard selftest, exit0;
  M42, R/tz/y20 приняты на уровне аргументов, H0/неверный dt отвергнуты.
- Новый `P10FN_physics_audit` повторно проверил настоящие 5 CSV M2:
  `3.059005330300839 m⁻¹`, pass для 7206 строк, 10094 Tet10.

**Честная граница проверки:** в текущем Linux-окружении нет запускаемой
Gmsh 4.15.2 Windows и MinGW; native M3 generation на компьютере
исследователя ещё не исполнена. Поддержка `tz/y20` прошла native guard
selftest, но физический результат этих мод на M3 ещё не проверен.
До получения первого P10FN evidence нельзя объявлять скрипты Windows
или M3 геометрию окончательно нативно подтверждёнными.

## Ориентиры времени на i7-7700K (не норматив)

- M3 Gmsh: оценка 2–15 минут, hard stop 15 минут;
- M3 физика близкого к M2 размера: ориентир 3–15 минут,
  hard stop 6 часов для будущих более крупных MN;
- прогноз не заменяет проверку RAM, диска, SHA и нативных логов.

## Состав

- `research/packages/P10FN_GENERAL_MESH_AND_PHYSICS_WINDOWS_20261122.zip`
  — полностью автономные C++/Python/.cmd исходники с SHA-inventory;
- `research/proposals/P10FN_GENERAL_WINDOWS_20261122/`
  — исходные сценарии, начальный C¹-рецепт M3, первоначальные одобрения
  M0/M1/M2 и сборщик автономного архива;
- техническая инструкция внутри пакета `README_RU.md`.

Следующий живой шаг: пользователь кладёт оригинальную `M2.msh` в
фиксированный `meshes`, запускает `01_GENERATE_NEXT_MESH.cmd`,
присылает `P10FN_M3_MESH_EVIDENCE.zip`. После проверки геометрии
выдаётся SHA-pinned `approvals/M3.json`, и только тогда запускается
универсальная физика с M3. Следующий `recipes/ACTIVE.json` для M4
строится из **реального сравнения** M0/M1/M2/M3 после M3-физики.
