## Исходное состояние и цель

P10BM опубликовал пользовательскую Git-историю в `research/p10bi-local-seven-sources-20261119` при точном HEAD `90fd2559c0224ac0a7d2dbe2fe081a6a319080e4`. Отдельная P10BG ветка содержит те же байты 7 исследуемых исходных файлов (7/7 Git blob SHA). Windows P10BH подтвердил четыре **запуска старых EXE**, но не происхождение их сборки. На активном ПК оставались 7 unstaged + 4 untracked; их нельзя перезаписывать или удалять.

**Цель P10BN:** получить цепочку «известный чистый Git commit → фиксированная среда CMake/MinGW → свежие EXE с SHA-256 → независимые короткие unit/selftest», сохранив первичные логи. Это не попытка задним числом аттестовать прежние `.exe` или повторить тяжёлый P10BE FEM.

## Безопасная последовательность для Windows

1. В `G:\ildar\Stage3D07` только **прочитать** текущие HEAD/ветку/status; удостовериться, что неизменённые пользовательские 7 unstaged и 4 untracked не затрагиваются. Не выполнять `reset`, `clean`, `pull`, `merge`, `stash`, force-push.
2. Создать **новую независимую рабочую копию/второй worktree на другом пути**, строго привязав её к SHA `90fd2559c0224ac0a7d2dbe2fe081a6a319080e4`; не перестраивать старый `build/Desktop_MinGW_Release` и не менять текущий рабочий каталог. Команды или сценарий согласовать и проверить по наличию места и версии локального Git. При необходимости использовать свежий отдельный clone c GitHub, если он не перенесёт сторонних файлов из dirty дерева.
3. Убедиться, что `git status --porcelain` в **новой** копии пуст и `git rev-parse HEAD` равен указанному SHA. Зафиксировать Windows version, `cmake --version`, `g++ --version`, `mingw32-make --version` / Ninja, Qt Creator Kit/генератор/путь компилятора и все CMake параметры; не включать пароли и пользовательские секреты в публичный протокол.
4. Конфигурировать **новый** CMake build directory в MinGW Release и собрать конкретные короткие цели. Сохранить `CMakeCache.txt` либо его безопасный очищенный перечень критических параметров, полный configure и compile output, код возврата сборки и фактический timestamp. Перед публикацией логов проверить абсолютные локальные пути и конфиденциальные данные.
5. Рассчитать SHA-256 каждого **нового** EXE и запустить их из этой отдельной сборки, с сохранением stdout/stderr, exit code и командной строки:
   - `stage3d10v_analytic_shape_unit.exe`
   - `stage3d10y_analytic_shell_unit.exe`
   - `stage3d10be_temporal_unit.exe`
   - `stage3d10be_temporal_polar_audit.exe --selftest`
6. Проверить маркеры `*_UNIT_OK`, но не отождествлять `P10W_DEPENDENCY_SELFTEST_OK analytic_coupling_verified=0` с полной проверкой аналитической связи. Публиковать в исследовательской ветке **отчёт/метаданные** после сверки, не бинарники и не секретные абсолютные пути.

## Критерии приёмки

- Чистый source HEAD SHA, отсутствие изменений в отдельной копии **до** build; toolchain и CMake configuration однозначно записаны.
- Четыре EXE появились в новом каталоге сборки; их SHA-256, четыре command+exit code и полные тестовые выводы записаны как первичные факты. Если компиляция/тест упадут, записать точную ошибку и **не объявлять успех**.
- Старое пользовательское рабочее дерево осталось без изменений. Никаких больших FEM run; исходные P10BB/P10BE CSV сохранены неизменными.
- Полученная цепочка подтверждает новую сборку именно для P10BN, а не историческое происхождение P10BE_H2_LOGS_20261118_182525 или ранее созданных EXE.
