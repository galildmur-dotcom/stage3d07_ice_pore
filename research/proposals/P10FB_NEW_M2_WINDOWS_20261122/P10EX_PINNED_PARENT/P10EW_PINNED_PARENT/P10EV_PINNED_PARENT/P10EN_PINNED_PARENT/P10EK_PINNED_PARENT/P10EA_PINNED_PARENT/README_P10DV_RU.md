# P10DV R1 — исходная κ C¹, 20% объём: один плоский MathEval F6 без вложенных полей

**Статус SOURCE-ONLY:** в архиве **нет** запуска `gmsh.exe`, `-1/-2/-3`, M1/M2 meshing, FEM, пользовательского ввода one-shot, создания маркеров или открытия исходной M1 `.msh`. Результат — проверенный *кандидат исходного GEO*, не новая сетка M2 и не разрешение создавать её.

## Почему исправлена конструкция, но не сама физическая задача

В исходном Gmsh 4.15.2 `src/mesh/Field.cpp` (тег `gmsh_4_15_2`, Git blob `427911696c813c5543caa37b527a985775fa6d4e`) `MathEvalField::operator()` удерживает одну критическую секцию OpenMP, пока вычисляет зависимости `F3/F4/F5`. Вложенный MathEval повторно входит в ту же секцию и блокируется. Это объяснено в проверенном P10DU по оригинальным Windows журналам P10DT: A и C прошли за 0.213/0.208с, B с постоянным `F3=MathEval("0.5")` остановлен за 15.066с. Вложенные MathEval больше не используются.

Поле **P10DV_M2_INLINE_FIELD20.geo** построено *механической текстовой подстановкой* исходных выражений F3/F4 в F5 и затем F5 в F6 из **побайтно проверенного** исходного `P10DN_M2_FIELD20.geo`. Оно **не переопределяет** исходные Field1 Distance, Field2 Threshold, near/far и CAD: единственный MathEval теперь `Field[6]`; единственная ссылка на другое поле — `F2` (Threshold, а не MathEval). Нет Field3/Field4/Field5. Gmsh-синтаксис полной строки **на Windows нативно не проверялся**.

## Неизменённая научная постановка

Для каждой точки льда положим \(r^2=x^2+y^2+(z-0.03)^2\), \(\rho_\varepsilon=\sqrt{r^2+10^{-24}}\), \(d_\varepsilon=\rho_\varepsilon-0.001\), \(\mu_\varepsilon^2=(z-0.03)^2/(r^2+10^{-24})\) и \(S(t)=u^2(3-2u)\), \(u=\min(1,\max(0,t))\). Это **точная**, включая регуляризацию, математическая формула исходного GEO:

\[
\kappa=\bigl(1-S((d_\varepsilon-0.0001)/0.0004)\bigr)\,S((\mu_\varepsilon^2-0.36)/0.28),\quad
0\le\kappa\le1,\quad \kappa\in C^1.
\]

\[
\frac{V_{\mathrm{target},M2}}{V_{\mathrm{target},M1}}=1-0.20\kappa\in[0.8,1],\qquad
\frac{h_{M2}}{h_{M1}}=(1-0.20\kappa)^{1/3}\in[0.9283177667,1].
\]

Конструктивная проверка гладкости: \(S'(t)=6t(1-t)\) внутри интервала и **0 на обоих концах**, поэтому производная композиции непрерывна на границах clamp. В льду \(\rho\ge0.001\), знаменатели не обращаются в ноль, при полюсах нет угловой координаты φ и разрыва. Gmsh GEO содержит исходную регуляризацию `+1e-24`, которая не меняется. Значение κ и целевое **объёмное** соотношение остаются прежними; это не заявка на фактическое 20%-ное изменение попарных объёмов различных Tet10 после ремешинга.

**Принятая оригинальная M1:** только SHA256 `ca6b6b6588dc72c5dd3ed2e92e24794560ee2407e350c8a44858e9c3c7d0360f`, 9736 Tet10 — не H0/U0 и не новая M1. Исходные P10DO/P10DQ/P10DR/P10DT one-shot израсходованы, повтор и удаление маркеров запрещены.

## Проверка без Gmsh

1. При необходимости распаковать ZIP **в новую отдельную папку** вне `G:\ildar\Stage3D07` и старых попыток.
2. Можно **только** запустить `01_P10DV_SOURCE_MATH_ONLY.cmd`. Он проверит шесть SHA-источников, точную детерминированную подстановку, C¹ smoothstep, радиальную и полярную симметрию, независимую сферическую формулу и **17 075 точек ×3 базовых F2**. Успешный вывод: `P10DV_SOURCE_MATH_INLINE_C1_KAPPA20_PASS native_Gmsh=0 physical_FEM=0`.
3. Windows запуск пока **не нужен** и новых файлов для возвращения исследователем нет. Этот исходный ZIP уже проверен в изолированном тесте автора. Ни `gmsh.exe`, ни Qt Creator/FEM в комплект не входят.

**Граница:** Python-равенство полей в проверенных точках и аналитическая C¹ конструкция **не** заменяют Gmsh4.15.2 `-parse_and_exit`, native 1D runtime, M2 3D Tet10 curved27QP и 9-зонную объёмную QA. Будущий новый Gmsh mesh-only требует отдельного явного разрешения, нового source-pin/one-shot marker и предварительного безопасного parse/геометрического preflight. Новый physical forward/adjoint/FEM ещё более отдельный этап после принятия M2.
