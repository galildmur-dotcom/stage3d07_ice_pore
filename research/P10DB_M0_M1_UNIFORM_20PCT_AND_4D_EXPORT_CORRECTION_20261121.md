# P10DB — исправление P10DA: обязательный 4D-экспорт и вторая равномерная M1

**21.11.2026. Исправление по прямому замечанию исследователя. Реального нового FEM/Gmsh=0.** P10DA M0 на Windows уже запущен пользователем; не прерывать и не повторять автоматически. Решение D-018C заменяет действующие после D-018B рекомендации переходить непосредственно к adaptive M1.

## 1. В чём была ошибка при выборе EXE P10DA

С 20.11.2026 действует D-017: для shape-градиента нужны signed механические explicit/equilibrium/history и thermal mass/diffusion/Robin по физическим координатам **(r, θ, φ, t)** с раздельными объёмами/QP и global closure. Вместо полного экспортёра P10DA использовал прежний точно pinned Windows P10CA/P10BX EXE SHA `17c31f426245317271245e340d68fa5de1e4eb144b7be986167505e14cbed924` ради доказанной проверяемости global solver. **Это методическая ошибка ассистента: надёжность выбранного EXE не компенсирует недостаточный научный экспорт.** Никакой запрет физики/геометрии на φ-зависимый экспорт не существует.

Прямая проверка исходников:

- В `research/proposals/P10BX_THERMAL_QP_20261120/src/stage3d10p_partial_audit.cpp` P10BX расчёт thermal QP вызывается только для jpeak, `obs==1`; `P10BW_thermal_qp_partition.hpp` использует `std::array<Cell,100>`, где `shell_bin×polar_bin` (10×10). Физический azimuth bin отсутствует.
- В этой сборке не определён `STAGE3D10Y_ANALYTIC_SHELL_AUDIT`; в `src/stage3d10v_analytic_shape.hpp` механическая разбивка `objective_by_shell/equilibrium_by_shell` доступна только при этом условном флаге. Даже включённый P10Y разбивает лишь по **r**, не по (r,θ,φ). P10DA получает `P10W_COMPONENTS.csv` (global) и `P10W_STEP_COMPONENTS.csv` (global time), не mechanical 4D.
- `forward_history.bin` по исходнику `save_forward()` содержит для каждого шага `temperature`, `repinned_u`, `previous` (EDV QP history), а также финальное состояние. `reverse_scan()` вычисляет mechanical/thermal adjoints, но соответствующие полные поля по шагам в `forward_history.bin` **не записывает**. Файл `retained` — отдельная проверка восстановления финального состояния, не архив всей истории сопряжённых переменных.
- CLI `--reuse-forward` принимает сохранённый primal cache и позволяет сделать **новый обратный проход без повторного нелинейного прямого решения** при неизменных mesh/params. Но это повторный вычислительный проход, не простая переработка 606/6 CSV; бюджет/разрешение потребуются отдельно после P10DA evidence. Из первичных CSV однозначно восстановить φ-детализацию нельзя.

**Действие сейчас:** исходную Windows M0 попытку не трогать; после окончания исследователь передаёт **только P10DA_EVIDENCE.zip**. Все оригиналы `U0_PHYSICAL_RUN`, `forward_history.bin`, EXE, mesh должны оставаться на ПК, ничего не удалять. Если отсутствует кэш, фиксировать факт и не обещать восстановление.

## 2. Две последовательные РАВНОМЕРНЫЕ сетки без индикаторов

Исследователь установил: **M0=ранее U0 (h0=2мм), M1 — новая равномерная по всему объёму сетка с характерным объёмом элемента на ≈20% меньше, и лишь после физического M0+M1 возможна адаптация M2→...** Для M1 нет error-indicator selection, полярной или радиальной size-field, автоматического M1 от 4D бинов.

При одном семействе квазиодинаковых элементов `V∝h³`:

\[
h_1 = h_0(0.8)^{1/3} = 0.0018566355334451116\;\mathrm{m}=1.856635533445\;\mathrm{mm}.
\]

Подготовленный исходник `gmsh/P10DB_M1_UNIFORM_20PCT_VOLUME.geo` задаёт **один** constant `uniformSize=0.0018566355334451116` и подключает неизменённый `P10CS_U0_UNIFORM_VOLUME.geo`/исходную CAD/B6 геометрию. Сохранены MeshSizeMin/Max и отключены MeshSizeFromPoints/Curvature/ExtendFromBoundary; физические группы 1–9 и Tet10+MSH2.2 соответствуют P10CS.

Оценка N(Tet10) лишь объёмная: `90725/0.8≈113406`. Не гарантируется по Gmsh: независимая 3D генерация изменит элементы и их соответствия. После **одного отдельно согласованного mesh-only** построения M1 проверим медиану и распределение actual curved/straight Tet10 volumes на общей геометрии, physical groups, 27QP curved detJ и QP-угловые распределения. Нельзя требовать прямого соответствия K0↔K1 и точного уменьшения объёма **каждого** K на 20%: математически при remeshing это некорректное условие. **M1 физический FEM пока не запускать.** Его ресурсный бюджет уточним по M0 evidence; не запускать параллельно текущему M0.

## 3. Исправление программы: 4D-инструментирование как обязательный gate

Перед новой физической попыткой M1 — и перед возможным postprocessing M0 через `--reuse-forward` — нужно создать новый изолированный исходник/EXE с настоящим QP-накоплением:

1. Сетка ячеек `(shell=10, μ=10, φ=12, step=6)` = **7200 пространственно-временных ячеек на каждый компонент**, top Robin отдельно. В отличие от P10BX `100` ячеек/step, это `1200` пространственных клеток/step. Полюса обрабатываются по физическим curved-QP координатам, не corner-centroid и не полярным «предпочтениям» размера сетки.
2. На **27-QP mechanical Tet10** сохранить для каждого `(K,n)` и bin signed `explicit_objective`, `equilibrium`, `history`; normalisation B6 и история EDV должны в сумме совпадать с original `P10W_COMPONENTS/STEP_COMPONENTS` (из существующего P10Y radial-code generalization). На **64-QP thermal Tet10** сохранить signed `mass`, `diffusion`, объём/QP/температуру (расширение P10BW), а Robin top отдельной boundary-записью. Не смешивать механический и тепловой QP-count/volumes и не суммировать одинаковые QP повторно при трёх компонентах.
3. На каждом шаге и по всей истории проверить `Σ_{r,μ,φ}G^{alpha}_{cell,n}` против исходного точного algebraic CSR/local mechanical step result с заранее фиксированными нормированными допусками; отдельно global `Σ mech + Σ thermal` против `D_R jpeak`. Подписанные вклады и суммы модулей сохранять раздельно. Ориентация φ и пороговые координаты должны быть детерминированы.
4. **Сначала** isolated C++ build + native unit/replay/negative closure tests; лишь после — Windows SHA/ресурсно ограниченный протокол. Старый P10DA EXE **не заменять во время текущей работы**, не приписывать ему новые возможности задним числом.

Пока написан и проверен лишь **читаемый эталонный 4D-контракт**, не реальный FEM exporter: `research/proposals/P10DB_M1_UNIFORM_AND_4D_CONTRACT_20261121/p10db_4d_partition_contract.py`, с 10×10×12 картой, signed six-component sums, special top Robin, physical-QP volumes/counts, φ seam/pole tests, и отрицательным тестом нарушенного closure. Его synthetic `P10DB_4D_SYNTHETIC_PARTITION_OK ... FEM=0`; интеграция в реальные C++ QP-циклы **ещё не выполнена**. Нельзя называть M0 4D-восстановленным или M1 executable-ready.

## 4. Следующий порядок без подмены требования

1. Получить один уже идущий **M0/U0 physical evidence**, проверить и сохранить оригинальный `forward_history.bin` на ПК.
2. Реализовать и аттестовать 4D экспортер, оценить возможное недорогое восстановление именно *сопряжённого* прохода M0 с reuse-forward, согласовать ресурсный one-shot отдельно; если отказ — честно оставить M0 4D UNKNOWN.
3. Построить **одну M1 равномерную** c h1≈1.8566мм, проверить фактическое уменьшение размеров/объёмов и качество. Затем отдельный M1 physical run с полным 4D экспортом.
4. Сравнить M0/M1 глобальные механический/тепловой shape gradients, temporal contributions, QP/CSR, при наличии их сопоставимые 4D данные. **Только затем** разрабатывать M2 по проверяемым индикаторам погрешности, без заранее заданных конечных размеров/числа узлов.

Никаких Gmsh/FEM и изменений пользовательского Windows project в P10DB не было. Ключевой результат P10DB — **исправленное решение, точная M1 mesh-source и верифицируемый 4D export contract**, а не новые физические данные.
