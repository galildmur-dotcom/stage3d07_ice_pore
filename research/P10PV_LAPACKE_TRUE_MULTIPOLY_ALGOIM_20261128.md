# Stage3D07 — P10PV: LAPACKE доступна; настоящий многограничный Algoim работает

Дата проверки: 2026-11-28. Статус: **PASS_SOURCE_ONLY, PASS_CXX20_WITH_LOCAL_COMPAT_PATCH**.

## 1. Ключевой ответ на вопрос пользователя

Проблемы «LAPACKE невозможно получить/использовать» **не существует**. Это
поддерживаемый C-интерфейс к LAPACK с исходниками, документацией и готовыми
бинарными пакетами, включая Windows MinGW. Предыдущее затруднение P10PU было
ограничением тестовой среды и ещё не проверенной цепочки сборки, **не**
недостатком научного метода или недоступностью алгоритма.

Проверенные первоисточники:

- [Reference-LAPACK, официальные исходники](https://github.com/Reference-LAPACK/lapack),
  в том числе `LAPACKE/`.
- [Netlib: LAPACKE C interface, документация](https://www.netlib.org/lapack/lapacke.html),
  в том числе `LAPACK_ROW_MAJOR` и `LAPACK_COL_MAJOR`.
- [MSYS2: mingw-w64-x86_64-lapacke](https://packages.msys2.org/packages/mingw-w64-x86_64-lapacke),
  включая `lapacke.h`, библиотеку и DLL (пакет 3.12.1-2 на дату проверки).
- [MSYS2: mingw-w64-ucrt-x86_64-lapacke](https://packages.msys2.org/packages/),
  для другой среды исполнения. Сборки `MINGW64`, `UCRT64`, Qt Creator и
  MinGW необходимо согласовывать; случайные DLL из несовместимых комплектов
  нельзя смешивать.
- [Algoim: официальная документация multi-polynomial API](https://algoim.github.io/),
  `algoim::ImplicitPolyQuadrature<3>` / `AutoMixed`.

Для компьютера пользователя **ничего вручную устанавливать и запускать в
PowerShell сейчас не требуется**. Проверка выполнялась в отдельном Linux
окружении; будущий Windows-пакет должен либо включать согласованные исполняемые
библиотеки, либо обеспечить проверку установленного компилятора и ABI перед
запуском. Это отдельный упаковочный этап, не научное ограничение.

## 2. Что фактически удалось запустить

Использованы **настоящие** функции `LAPACKE_dgesvd`, `LAPACKE_dggevx`,
вызываемые оригинальным Algoim `quadrature_multipoly.hpp`. Ни заглушек для
SVD, ни подмены вычисления собственных значений нет. Algoim из коммита
`da1d81499608e1d499695d255f0233140b8c81e8`;
Reference-LAPACK из `d74c488c1d2ea1142ab1d89bd950121cb72d9722`.

Новые воспроизводимые файлы:

1. `research/tools/P10PV_ALGOIM_MULTIPOLY_SECTOR_SOURCE_ONLY.cpp` —
   последовательная проверка 1, 2, 3, 4 полиномиальных границ.
2. `research/tools/P10PV_ALGOIM_CXX20_COMPAT.patch` — небольшая явная
   конструкция `xarraySlice(T*, int)` внутри upstream `algoim/xarray.hpp`,
   устраняющая C++20 несовместимость в одной точке, без изменения математических
   операций. Это **локальная проверенная поправка**, не upstream-релиз.
3. `research/tools/P10PV_MULTIPOLY_SOURCE_ONLY_QA.py` — отдельная проверка
   компиляции, порядка квадратуры, веса, количества узлов и допустимых ошибок.
4. `research/P10PV_MULTIPOLY_SOURCE_ONLY_QA.json` — машинный протокол 24
   численных запусков, SHA исходного файла и библиотеки.

В нашей Linux-среде системная LAPACK оказалась старше нового интерфейса
`set_lapack_xerbla_` в части обработки ошибок LAPACKE. Свежий официальный
`liblapacke.a` собран из исходников, затем только обработчик ошибок
`lapacke_xerbla.c` перекомпилирован с `-ffunction-sections`, а конечная
сборка использовала `-Wl,--gc-sections` для исключения невызванного кода.
**Численные процедуры LAPACK и LAPACKE не изменялись**. В Windows при
согласованных пакетах этой временной технической меры не предполагается.

Первичная компиляция `g++ -std=c++17` прошла; C++20 на *неизменённом*
Algoim отвергает инициализацию `xarraySlice{ptr,len}` из-за правила агрегатной
инициализации. После применения отдельного маленького патча сборка
`g++ -std=c++20` тоже прошла; её результаты в таблице ниже равны результатам
C++17. Следовательно, это **совместимость заголовка Algoim, не LAPACKE**.

## 3. Геометрия независимого теста

Только синтетическая геометрия. Нет ни CAD, ни генерации сетки, ни FEM,
ни EDV или adjoint; здесь **нельзя** утверждать сходимость реальной модели M21.

В декартовом первом октанте `[0,1]^3` последовательно пересекались:

1. Внешняя сфера: `x²+y²+z² <= 1`.
2. Полярный конус: `z² >= μ0²(x²+y²+z²)`, `μ0 = 0.8`.
3. Азимутальная плоскость: `y <= tan(π/3)x`.
4. Внутренняя сферическая граница: `x²+y²+z² >= (r0/r1)²`,
   `r0 = 0.08`, `r1 = 0.22`.

Масштаб координат для интеграла — `r1`, поэтому точный объём полного
фрагмента (в синтетических единицах)

`V_exact = ((r1^3-r0^3)/3) × (1-μ0) × (π/3)`

`        = 0.000707626291928581`.

Всё это — **четыре настоящих полиномиальных уровня** в одном объекте
`ImplicitPolyQuadrature<3>`, а не замена многограничного геометрического
интегрирования последовательными эвристическими отсечениями.

У всех 24 комбинаций (1–4 границы × 6 порядков) все веса **строго
положительны** (наименьший вес может быть крайне мал), а сумма весов
всех фаз равна объёму контрольного куба с допуском `1e-7` относительно
его объёма. Автоматический QA успешно прошёл на C++17 и C++20.

**Честная оговорка о сходимости:** отдельно для конфигурации только
«сфера + конус» (`n_poly=2`) ошибка `q=6` равнялась
`9.7404e-4`, `q=8` — `9.1859e-4`, но `q=12` — `1.2562e-3`.
Она не монотонна. Вероятная причина, требующая проверки, — особая
геометрия вершины конуса/границы октанта и разбиение на фазы. Это не
отменяет успешной сходимости полного четырёхграничного примера, но
не позволяет заявлять безусловную сходимость **всех** пересечений.

## 5. Ограничение производительности и следующий этап

`q=12` в одном цельном кубе генерирует **2.14 млн узлов**. Нельзя
просто умножить это число на ~43 200 тетраэдров M21 и считать метод
готовым к FEM. Для практического внедрения потребуются:

- отсев тетраэдров, которые целиком внутри/снаружи геометрии (без costly
  multi-boundary integration), и отбор только пересекаемых ячеек;
- раздельная обработка обычных одно-/двухграничных пересечений и
  редких многограничных ячеек, в том числе вблизи полюсов;
- адаптивный выбор `q` по локальной невязке/оценке ошибки;
- точное отображение и Якобиан исходного криволинейного Tet10 в каждой
  квадратурной точке; проверка ориентировки, знака и сохранения массы;
- независимая геометрическая сверка с аналитическими интегралами
  и только **после этого** физика и FEM/EDV;
- для будущих связанных операций с сеткой обязательно сохранять
  заданную пользователем стратегию Gmsh **HighOrderElastic**.

**Предлагаемый P10PW (пока не выполнен):** добавить отсечение исходным
референсным симплексом `u+v+w<=1` и независимую проверку аналитического
объёма на прямом Tet10; затем аккуратно перейти к реальному криволинейному
Tet10 из M21 и исследовать затраты/точность с локальной полярной геометрией.
Физическую программу и тяжёлые расчёты до прохождения этих QA не запускать.

## 6. Проверяемость

При наличии согласованных локальных исходников `Algoim`, `LAPACKE` и
`LAPACK/BLAS` команда эквивалентна:

```bash
# Для C++20 сначала применить соответствующий компактный патч к Algoim:
git -C ALGOIM_ROOT apply PATH/TO/P10PV_ALGOIM_CXX20_COMPAT.patch

python3 P10PV_MULTIPOLY_SOURCE_ONLY_QA.py \
    --algoim-root ALGOIM_ROOT \
    --lapacke-include LAPACK_ROOT/LAPACKE/include \
    --lapacke-lib LAPACK_ROOT/liblapacke.a \
    --lapack-lib /path/to/liblapack.so \
    --blas-lib /path/to/libblas.so \
    --std c++20
```

Не является Windows-инструкцией для пользователя. Цель — воспроизводимый
научный исходный код и QA в исследовательской ветке.
