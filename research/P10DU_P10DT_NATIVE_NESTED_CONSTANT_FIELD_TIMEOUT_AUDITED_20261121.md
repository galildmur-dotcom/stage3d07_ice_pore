## 3. Причина в исходном коде Gmsh 4.15.2 — статически обнаружена

P10DR: F2 сам по себе быстро завершался, а исходные F3-only и F4-only через F6 оба останавливались за15s. P10DT разделяет два механизма: **в B пространственной переменной нет, но есть ссылка на MathEval F3; в C пространственное `min/max/sqrt` есть, но нет вложенной ссылки.** Следовательно, для наблюдённого STOP **пространственный clamp не является необходимым условием**.

После аудита **статически изучен именно тег `gmsh_4_15_2`** официального read-only GitHub mirror [`gmsh-project/gmsh`](https://github.com/gmsh-project/gmsh/tree/gmsh_4_15_2). Файл [`src/mesh/Field.cpp`, Git blob `427911696c813c5543caa37b527a985775fa6d4e`](https://github.com/gmsh-project/gmsh/blob/gmsh_4_15_2/src/mesh/Field.cpp), две причинно связанные точки:

1. [`MathEvalExpression::evaluate`, строки 1021–1041](https://github.com/gmsh-project/gmsh/blob/gmsh_4_15_2/src/mesh/Field.cpp#L1021-L1041): для каждого `F<n>` получает `Field*` и **синхронно вызывает** `(*field)(x,y,z,ge)`.
2. [`MathEvalField::operator()`, строки 1153–1175](https://github.com/gmsh-project/gmsh/blob/gmsh_4_15_2/src/mesh/Field.cpp#L1153-L1175): весь `_expr.evaluate` находится внутри **именованной OpenMP критической секции** `critical(MathEvalField)`. Комментарий разработчика прямо предупреждает о **нереентерабельности** и невозможности ссылки на другое поле MathEval.

**Механизм:** обработка F6 захватывает `critical(MathEvalField)` → во время `_expr.evaluate` ссылка `F3` вызывает `MathEvalField::operator()` для F3 → тот повторно пытается войти в **ту же** именованную критическую секцию до её освобождения. При активном OpenMP эта вложенность приводит к самоблокировке. В варианте A и C внутри `MathEval` вычисляется только `F2` типа `Threshold`, поэтому повторного входа в `MathEvalField` нет; оба проходят. Это же объясняет P10DQ B (`F6="F2"`, быстро) и зависание оригинальных F3/F4/F5-цепочек. **Таким образом, установлена конкретная исходниковая причина, согласованная со всеми наблюдениями P10DQ/P10DR/P10DT.**

**Оговорка воспроизводимости:** исходники тега и их blob SHA независимо прочитаны, но точный Windows exe SHA сообщён в манифесте пользователя; сами байты `.exe`, компилятор/OpenMP build flags, CPU stack и независимая бинарная аттестация отсутствуют. Поэтому перенос статического объяснения на фактический exe обоснован наблюдениями, но не проверкой сборки байт-в-байт. `-nt 2` не устраняет проблему: это вложенный вызов той же критической секции, а не состязание между двумя потоками.

В официальной документации Gmsh 4.15.2 `MathEval` ссылки `F0,F1,...` **синтаксически** разрешены (в tutorial t10 приведён пример MathEval через значение другого поля). Документация и конкретная реализация имеют важное различие: вложение через другое **MathEval** в данной версии не поддерживается из-за OpenMP критической секции. Это не ошибка написания `F3` и не доказательство неверности κ. Ключи `-v/-log/-cpu` не устраняют самоблокировку. Из этого исследования никакой вывод о фактической κ в геометрии нового M2 не следует.

## 4. Решение о дальнейшем научном шаге

**P10DT завершён, повтор запрещён.** Статическое исследование Gmsh выполнено. Следующий безопасный этап — **только source-only** подготовка **flattened** размерного поля, в котором исходная κ C¹ радиально-полярная формула написана непосредственно в F6 без промежуточных `F3/F4/F5`. Требуется математически показать эквивалентность на всём домене и прежний предел целевого объёма:

\[
\kappa(x)\in[0,1],\qquad \kappa\in C^1,\qquad
\frac{V_{\mathrm{target},M2}(x)}{V_{\mathrm{target},M1}(x)}=1-0.20\kappa(x),\qquad
\frac{h_{M2}(x)}{h_{M1}(x)}=(1-0.20\kappa(x))^{1/3}.
\]

Это **предложение кандидата**, не подтверждённая native исправленная M2. Отдельный Windows mesh-only `-1`/`-3` возможен только после явного нового разрешения, предварительного safe GEO parse, одного нового marker и ограничений. Долгие 3D native попытки и вся physical FEM закрыты до выяснения вопроса с размерным полем и новой геометрической QA. Оригинальные M1/H0/forward cache и старые маркеры не трогать.
