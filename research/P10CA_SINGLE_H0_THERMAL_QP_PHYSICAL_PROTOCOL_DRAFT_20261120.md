# P10CA — проект протокола одной физической H0 thermal QP/CSR пробы (НЕ ЗАПУСКАТЬ)

**Дата:** 20.11.2026. **Статус:** `DRAFT_APPROVAL_REQUIRED`, только исходный аудит и ресурсный план; **0 новых физических solve**, 0 новых Windows действий. P10BZ R2 native Windows 2/2 завершён. Протокол **не является разрешением** на H0 и не поставляет физический One Click.

## Научный вопрос

На реальной H0 Tet10 геометрии, для радиального поля `V·n>0` (расширение поры), EDV с температурно-зависимым мгновенным модулем (`VAR`), фиксированного детерминированного сценария **ξ=0** и `6×150 s` (горизонт 900 s): будет ли полная обратная thermal adjoint составляющая `D_R j_peak` точно воспроизведена **локальными** QP массой/диффузией/Robin в 10 radial ×10 polar бинах плюс отдельный внешний top Robin, по каждому физическому временному шагу и в сумме? Где сконцентрирован первый наблюдаемый вклад по расстоянию от стенки, без заявления о сходимости по сетке?

## Проверенный контракт кода и будущая конфигурация

* Источник для production pilot — **изолированный build** exact P10BX diagnostic P10P + `stage3d10w_analytic_adjoint.cpp`, при одновременных compile-definition `STAGE3D10W_ANALYTIC_SHAPE` (определена в исходном W) и **opt-in** `STAGE3D10BX_THERMAL_QP_DIAGNOSTIC`, с P10BW header и историческим Win32 `win_process_memory.cpp`+`Psapi`. Не заменять файлы в грязном `G:\ildar\Stage3D07` и не использовать R2 unit-only EXE как физический solver.
* Точный `p10k::setting()` source задаёт `EDV`, `VAR`, Gauss QP=3, peak exponent `p=8`. P10P thermal reverse использует `H::ambient(n*dt,0.)`, то есть единственный детерминированный `ξ=0`. Форменная скорость — `p10v::velocity(mesh,"R",5)` с аналитической Tet10 производной, никаких центральных FD mesh.
* После будущей точной проверки mesh path/SHA и source/EXE provenance параметры полного физического исполняемого файла будут: `--mesh <VERIFIED_H0_MSH> --out <NEW_ISOLATED_DIR> --steps 6 --dt 150 --mode R --cutoff-mm 5 --threads 4`. Это **схема, не команда для выполнения сейчас**. P10W wrapper **запрещает** `--delta-scan-um`, вызывает `p10n::run(c,{0.})` — значение 0 означает аналитическую скорость, а не нулевую физическую пору.
* `--preflight` **не является сухим запуском**: в `p10n::run` перед проверкой `c.preflight` вызывается `H::solve_forward`. Поэтому нельзя запускать его без согласования, даже отдельно от полного пилота.

## Фактическая H0 основа и оценка ресурсов (до нового измерения)

Из уже архивного `samples/P10M_H0_DT150.csv`: H0 примерно **10845 узлов**, **7388 Tet10**; исторический P10W H0/R `~109.77 s` (другая сборка, не измерение новой). Для 6 шагов ожидается `7388×64×6 = 2 836 992` объёмных thermal QP; неизвестное число top Tri6 даёт дополнительно `96×N_top` Robin QP. Диагностические CSV: **6×(100 radial/polar +1 top)=606** строк `P10BX_THERMAL_QP_STEP_BINS.csv`, **6** строк `P10BX_THERMAL_STEP_AUDIT.csv` без заголовков. Это прогноз количества, реальные H0 mesh/топология и output требуют повторной сверки.

**Предварительный бюджет, не runtime promise:** 2–6 минут низкой достоверности, контрольный резерв **10 минут**, память **не более 8 GiB**, новый диск **не более 1 GiB**. Текущий P10P оценивает буферы и останавливается по внутреннему лимиту 10 GiB, **но не реализует реальное ограничение RSS/диска/времени**. До разрешённого run потребуется отдельный безопасный wrapper-supervisor или ручной явный STOP, чтобы не выдавать желаемый предел за автоматическую гарантию. Параллелизм не более 4 OpenMP потоков, VTU выключены, не запускать H1/H2 или несколько дельт.

## Критерии принятия и остановки

1. **До solve:** отдельное разрешение исследователя; зафиксировать актуальный Windows Git HEAD/status/fingerprint; SHA-256 H0 `.msh`, `src` и нового физического EXE, MinGW/CMake version, полный args, независимый каталог вне исходной папки. Если mesh или source provenance UNKNOWN, **STOP**.
2. **Ровно один физический сценарий:** EDV/VAR, R, `ξ=0`, `steps=6`, `dt=150`, один H0. Не менять утверждённые material/geometry/near-pore B6 определения. Ни GH3, ни temporal/spatial campaign пока.
3. **Per-step:** `P10BX_THERMAL_STEP_AUDIT.csv` содержит 6 времён и действительные CSR/QP decomposition; по исходному коду step error `abs(qp−csr) ≤ 1e−10+1e−8×scale`, массы и немассовой суммы — тоже. `thermal_qp_count` ожидается `7388×64` на шаге при подтверждении того же H0. Все числа конечны; top Robin записан **отдельно**, не в near-pore 100 ячеек.
4. **All-step:** обязательные `P10BX_THERMAL_QP_INTEGRATED_OK ... steps=6 bins_per_step=100 top_robin_rows=6 exported_rows=606 original_gradient_unchanged=1`, `P10W_ANALYTIC_ADJOINT_OK`, `geometry_partial=ANALYTIC_TET10`, `central_fd_evaluations=0`, `mechanical_adjoint_solves=18`, native exit0. Сумма проверяется `|Σ QP−CSR| ≤ 1e−8 max(1,|CSR|)+6e−10` по source.
5. **Ресурсный STOP:** непредвиденный рост памяти/диска, отсутствие маркеров, fail `P10N_ERROR` или `P10W_ERROR`, неположительный Tet10 Jacobian, QP/CSR discrepancy или отказ Newton — не повторять вслепую. Исходный Windows worktree должен остаться неизменным.
6. **Передать только компактные свидетельства:** `P10BX_THERMAL_QP_STEP_BINS.csv`, `P10BX_THERMAL_STEP_AUDIT.csv`, `P10W_ANALYTIC_ADJOINT.csv`, `P10W_COMPONENTS.csv`, `P10W_STEP_COMPONENTS.csv`, краткий `RESULT` и `RUN_MANIFEST` внутри **одного** небольшого evidence ZIP. Не передавать MSH, `forward_history.bin`, checkpoints, EXE, VTU; для них сохраняются хеши и пути локально.
