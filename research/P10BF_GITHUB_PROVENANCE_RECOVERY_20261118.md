Пакет: `tools/P10BF_ONECLICK_EXPORT_20261118.zip`, SHA-256 `ddf99a84b63645841e7a26217c58ac7c2bcf21369dabc333f4c52bfc98521789`. `unzip -t` — OK. Пройден `P10BF_COLLECTOR_SELFTEST_OK` для всех трёх классификаторов CSV; тестовая упаковка на актуальном GitHub-дереве — OK (4 из 5 файлов и 0 CSV ожидаемы, потому что в нём отсутствуют P10BA header и три первичных CSV). **Windows/PowerShell/Qt на машине пользователя не тестировались**; полная сборка исходников P10AZ–P10BE пока невозможна из одного GitHub HEAD.

Классификация трёх P10BB-оригиналов выполняется по сумме механических вкладов последнего шага в двух оболочках 0.020–0.100 мм:

| Сетка | Ожидаемая сумма t=900 с, м⁻¹ |
|---|---:|
| H4W4B2 | −0.735338450892 |
| H4W4B20 | −0.734183561239 |
| H4W5B2 | −0.740080366816 |

Требования к кандидату: 400 строк, 200 ячеек на шаге 6, уникальные ключи. Если несколько различных файлов соответствуют одной сетке, автоматический выбор запрещён: в манифесте должна остаться пометка об неоднозначности.

## После получения экспорта

1. Сопоставить пять исходников с GitHub и патчами P10BD/BE; установить, воспроизводится ли точная логическая цепочка изменений. В отдельной контрольной копии выполнить `git apply --check`, unit/selftest и независимый анализ разностей. Не приписывать старому EXE новый Git SHA без дополнительных свидетельств.
2. Для P10BB пересчитать из трёх исходных CSV `P10BB_SPATIAL_COMPARE.csv`, `P10BB_HOTSPOT_CONSISTENCY.csv` и полярные доли; сохранить исходники, SHA-256, явные балансы и тип используемых временных вкладов.
3. Лишь затем исправлять инфраструктуру manifest для **будущих** запусков и текущую сводную документацию. Старые `RUN_MANIFEST.json` и исторические решения оставить неизменёнными.

## Ограничения

Отдельный экспорт не доказывает идентичность файлов на дату сборки Windows .exe. Программное тестирование в среде подготовки — только Python selftest; ни один тяжёлый FEM и ни одно изменение пользовательского Windows-кода не выполнены.
