# AGENTS — правила сопровождения проекта Stage3D07

Проект: «Исследование и статья Пора — 3Д сфера». Цель — самостоятельная научная работа о геометрической чувствительности термомеханической задачи пресноводного льда со сферической внутренней полостью.

**Действующая процедурная инструкция — [`docs/STAGE3D07_WORKING_SOP_RU.md`](docs/STAGE3D07_WORKING_SOP_RU.md).** Перед изменениями и в новом чате прочитать её вместе с `master/START_NEW_CHAT.md`. Настоящий `AGENTS.md` задаёт постоянные научные и защитные ограничения; хронологические «следующие шаги» в старых документах не перекрывают актуальный регламент. Проверять удалённый HEAD, а не полагаться на SHA из прошлых чатов.

## Научные ограничения

1. Сохранять постановку: 3D, квазистатическая механика, нестационарная теплопроводность, GH3; сравнения E/ED/EDV и E_inst CONST/VAR.
2. Главный предмет — **геометрические** производные и градиент формы. Параметрическая чувствительность не должна подменять эту задачу.
3. Исключить центральные конечные разности из основных геометрических частных производных; оставить их только в независимых тестах. Любое заявление о реализации подкреплять проверкой актуального кода.
4. Не считать строку `..._OK` доказательством пространственной сходимости, корректности реологии или применимости критерия прочности. Отмечать уровень каждого доказательства.
5. Не сравнивать результаты с неопубликованной 2D задачей цилиндрической поры и не ссылаться на неё в самостоятельной статье.

## Данные, выводы и сохранение

- Короткие отчёты и проверенные CSV идут в Git; большие `.msh`, `.vtu`, `.bin`, checkpoint и многогигабайтные истории — вне Git.
- Каждый значимый запуск связывать с фактическим run_id, аргументами, сеткой и Git SHA, если SHA действительно известен.
- Для новых запусков Stage3D10S использовать `RUN_MANIFEST.json` (этап M01): различать `preflight_ok`, `completed` и ошибочные состояния; не считать предварительный запуск полноценным экспериментом.
- После действительно завершённого запуска вносить запись через отдельную цель `ice3d_register_manifest` (этап M02): сначала `--dry-run`, затем запись. Запись не производится автоматически при выходе FEM; проверить, что в реестре нет дубликата `run_id`.
- Значение `git_commit_at_cmake_configure` из паспорта — версия, прочитанная во время конфигурации CMake, а не доказательство чистого дерева при сборке или запуска того же бинарника. Для строгой воспроизводимости фиксировать дополнительно SHA-256 exe, сетки и состояние дерева.
- В `RESEARCH_LOG.md` различать факт, гипотезу, вывод после анализа; в `DECISIONS.md` сохранять причину методического выбора.
- Копии ценных расчётов размещать на F по `docs/F_ARCHIVE_PLAN.md`; не считать разные буквы дисков физической независимостью без проверки.
- Правила и границы автоматизации M01/M02 собраны в `docs/PIPELINE_M01_M02_RU.md`. Не назначать историческим расчётам новые паспорта задним числом без подтверждающих журналов.
- Перед переходом в новый чат обновлять `docs/PROJECT_STATE.md` и перечень открытых задач.
- Для каждой публикации фиксировать точный GitHub commit и читать обновлённый файл с удалённой ветки; затем синхронизировать `master/START_NEW_CHAT.md`. Не сливать независимые истории `master` / `research/p10bb-w5b2-20261118` / `research/p10bi-local-seven-sources-20261119` автоматически.

## Распределение ответственности

Ассистент разрабатывает и проверяет научные документы/код/скрипты, анализирует доказательства и **может публиковать разрешённые проверенные изменения на GitHub** с последующей сверкой. Исследователь утверждает научные решения и ресурсные FEM-опыты, запускает Windows-проверки на своём ПК, подтверждает результаты и выполняет только заранее согласованные локальные Git/архивные операции. Доступ к локальным `G:`/`F:` у ассистента не предполагается. Опасные операции, force/merge, очистка пользовательского дерева, публичная отправка новых категорий данных требуют отдельного решения.
