# Stage 3D-09E — экономный вывод для больших FEM-сеток

25.10.2026. Обновление основано на Stage 3D-09D5 (исправленный chunked restart), Stage 3D-09D4 (HP2/HP4/HP8) и Stage 3D-09D3 (диагностика).

## Что меняется

1. **Бинарные узловые температуры** `thermal_<t>s.p09e`: одна сетка читается из `.msh`, а на каждом шаге записываются только `double` dT (без копирования координат, связности и трёх почти одинаковых массивов температуры). Header: magic, версия, число узлов, FNV-64 подпись координат и связности, время в секундах, FNV-64 сумма содержимого. Запись блоками по 16 MiB во временный файл `.part` с последующим переименованием. Полное чтение валидирует подпись сетки, время, содержимое и отсутствие лишних байт. Формат **не сжатый**, точность IEEE754 binary64 сохраняется побитно.
2. **Механический VTU-вывод** `--vtu none|final|all`, по умолчанию не изменён (в запускателе legacy = `final`). `none` полностью исключает штатные `mechanics_<t>s.vtu`, но сохраняет функционалы и контрольное EDV-состояние.
3. **Независимая кампания** `--storage compact` пишет в `LOCAL_RUNS/SHAPE_STAGE09/P09E`, не затрагивая прежние `P09C`.
4. Механический решатель автоматически читает `.p09e`, если файл существует, иначе прежний `thermal_<t>s.vtu`. Постпроцессинг из `restart.bin` также поддерживает `.p09e`.
5. **Надёжное возобновление EDV**: остаётся действующий механизм сохранения `restart.bin` после каждого законченного шага с блочной записью Stage 3D-09D5. Контрольные состояния **не удаляются автоматически**. Периодическое редкое checkpointing / Revolve для будущей сопряжённой задачи в эту версию не входят.

## Установка

Остановить все расчёты. Распаковать PATCH в родительский каталог проекта (например `C:\Users\Admin\Downloads`) с заменой шести исходников и файла CMake. Папку `LOCAL_RUNS` не удалять.

В Qt Creator выбрать **Desktop MinGW Release**, выполнить CMake Reconfigure и собрать цели `stage3d09e_io_test`, `stage3d09c_shape_three`. Вторая цель также собирает `stage3d02_thermal` и `stage3d06_spatial`.

### Проверка перед запуском многосуточного HP8

Цель `stage3d09e_io_test`: запуск **без аргументов**. Ожидается:

```
P09E_IO_SELFTEST_OK bit_exact=1 wrong_mesh=reject wrong_time=reject checksum=verified
```

Цель `stage3d09c_shape_three`: `--selftest`. Ожидается `P09C_SELFTEST_OK`.

Короткая сквозная кампания на H0 (EDV/VAR, только 300 с):

```
--mesh H0 --modes y20 --laws EDV --moduli VAR --dt 300 --tend 300 --quad 3 --peak-p 8 --delta-um 5 --cutoff-mm 5 --threads 4 --reuse-p08d off --storage compact --mechanical-vtu none
```

При успехе вывод появится в `LOCAL_RUNS/SHAPE_STAGE09/P09E/H0_dt300_q3_t300_GH3_p8_delta5p000um_modesy20_lawsEDV_EVAR/`. Во вложенных папках `thermal` должны находиться `thermal_300s.p09e`, но **не** `thermal_300s.vtu`; механических полных VTU не должно быть. Итоговые маленькие CSV сохраняются как прежде. Для первого запуска в Windows рекомендуется прислать `P09C_STATUS.txt` и последние строки консоли, не запускайте сразу HP8.

### Полная HP8 (после успешной проверки)

Цель `stage3d09c_shape_three`, аргументы:

```
--mesh HP8 --modes y20 --laws EDV --moduli VAR --dt 300 --tend 3600 --quad 3 --peak-p 8 --delta-um 5 --cutoff-mm 5 --threads 4 --reuse-p08d off --storage compact --mechanical-vtu none
```

Выходная папка: `LOCAL_RUNS/SHAPE_STAGE09/P09E/HP8_dt300_q3_t3600_GH3_p8_delta5p000um_modesy20_lawsEDV_EVAR/`. Тепловые поля для HP8: 3 996 868 узлов × 8 байт ≈ 30.49 MiB/шаг; 72 поля ≈ 2.14 GiB без учёта метаданных. `restart.bin` приблизительно 6.9 GiB на траекторию и остаётся обязательным для работы запускателя. Производительность самого FEM-решателя этим обновлением существенно не меняется.

## Обратная совместимость и ограничения

- Без `--storage compact` программа сохраняет прежнее поведение теплового решателя и путь `P09C`.
- Наличие старых `thermal_*.vtu` позволяет считывать старые расчёты; новая кампания не смешивается с ними.
- Совпадение результатов **не побитовое** между старым VTU ASCII и новым `double`: старый VTU округлял значения до 12 значащих цифр. Это небольшое численное изменение, а не изменение физической модели.
- В случае обрыва **во время тепловой траектории** автоматическое продолжение с промежуточного температурного шага пока не реализовано. В случае остановки **механической траектории** `--resume` по последнему полному `restart.bin` сохранён.
- Из-за слабой сходимости производной `jpeak` необходимо выполнять ранее согласованную сеточную верификацию. Новое хранение само по себе не решает эту проблему.
- Пересборка и запуск под Windows MinGW после переноса патча должны быть подтверждены пользователем.

## Результаты локальных тестов

- C++20 selftest: побитная сохранность трёх doubles, отказ при неверном времени/геометрии, контроль повреждённого payload.
- Реальный H0, t=300 с: отклонение нового бинарного температурного поля от прежнего VTU с 12 цифрами вывода не более `5e-13` K.
- На H0 E/CONST один шаг 300 с: `j6`, `jpeak`, `jen` между прежним VTU и новым форматом согласуются в относительных величинах лучше `3e-9` (для jpeak moment); объём B6 совпадает.
- `--vtu none`: штатный механический VTU не создаётся, checkpoint и функционалы сохраняются.
- `--postprocess-only`: диагностический VTU и CSV восстановлены по checkpoint с компактной температурой.
- Linux C++20 компиляция `stage3d02_thermal`, `stage3d06_spatial`, `stage3d09c_shape_three`, `stage3d09e_io_test` выполнена в тестовой (без затратной O3) сборке; реальный HP8 в этой среде не рассчитывался.
