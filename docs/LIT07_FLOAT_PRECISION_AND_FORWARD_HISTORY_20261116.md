# LIT-07 — точность арифметики и возможность повторной постобработки прямой истории EDV

Дата: 2026-11-16. Режим: аудит актуального C++ из GitHub, независимая арифметическая проверка опубликованных первичных CSV; **без новых FEM-решений**.
Исходный подтверждённый Git HEAD: `95b45ce330daf6b6d7eb27960917535e7ed7b332`.

## 1. Точный ответ о типах данных в Stage3D07

**Основная вычислительная арифметика программы — `double` (IEEE 754 binary64 в стандартной Windows x86-64 конфигурации).** Фактически используются:

- `src/ed_material.hpp:13–14`: `Tensor = std::array<double,6>`, `Matrix = std::array<std::array<double,6>,6>`.
- `src/edv_material.hpp:21`: `State{Tensor e_d, e_v}` — 12 значений double (обычный `sizeof(State)=96` байт, однако фактический размер проверяется заголовком cache).
- `src/spatial_reology.cpp:29–31`: перемещения `std::vector<double> u`, температуры `vector<double>`, физические и функциональные интегралы double; `src/mechanical.cpp` — BCSR `array<double,9>`.
- `src/stage3d10e_bcsr_adjoint.hpp:133–135`: скалярное произведение итерационного решателя аккумулируется в `double sum`.
- `src/stage3d10v_analytic_shape.hpp:61–62,97,142,177–203`: `double observed_volume`, `observed_volume_derivative`, `std::vector<double> numerator, d_numerator`, квадратурные якобианы и дискретная форменная производная — double.
- `src/stage3d10p_partial_audit.cpp:746,769,795`: `std::setprecision(17)` в файлах градиента, компонент и временного разложения; это соответствует надёжной текстовой записи double для round-trip, но **не гарантирует 17 физически верных цифр**.
- `src/stage3d10h_retained_history.hpp:54–75` использует `long double` при оценке размеров снимков и бюджета диска, не при вычислении состояния EDV.
- `CMakeLists.txt:1124–1137`: для P10W задано `-O2 -Wall -Wextra -Wpedantic` с MinGW/GCC, без явного `-ffast-math` в этом блоке. При этом внешние/наследуемые CMake-флаги и фактический бинарник Windows ещё не проверены: окончательное утверждение о режимах FP требует отчёта о сборке.

Характеристики IEEE binary64: 64 бита хранения, 53 бита мантиссы (включая ведущий бит), 15–16 обычно надёжных десятичных значащих цифр, 17 цифр для однозначного round-trip; epsilon = 2^-52 = 2.220446049250313e-16, единичная ошибка округления u=2^-53=1.1102230246251565e-16. `long double` **зависит от компилятора и ABI**: для многих сборок GCC x86-64 хранение расширенного 80-битного формата занимает 16 байт, мантисса 64 бита (~18–19 цифр); для MSVC long double обычно равен double. Не следует считать `long double` автоматически 128-битной арифметикой. Точная локальная проверка возможна через `std::numeric_limits<double/long double>::digits`, `digits10`, `max_digits10`, `sizeof`.

## 2. Пилотная арифметическая проверка на первичных данных

**Источники:**
- `experiments/P10AC_H4W5B2_R_20261114/input/P10W_W4_COMPONENTS.csv`
- `experiments/P10AC_H4W5B2_R_20261114/input/P10W_W5_COMPONENTS.csv`
- `experiments/P10AB_H4W4B20_R_20261114/input/P10W_H4W4B20_COMPONENTS.csv`

Для строки `functional=jpeak` сложены четыре сохранённых с 17 цифрами части: `explicit_objective_shape_per_m`, `equilibrium_residual_shape_per_m`, `internal_history_shape_per_m`, `thermal_adjoint_per_m`.

Выполнены два способа суммирования: стандартный IEEE binary64 (Python float) и 65-значная десятичная арифметика Decimal **над одними и теми же напечатанными значениями**. Это проверяет заключительную операцию над сохранёнными CSV, **не** точность сборки квадратичных элементов, Q3, EDV-истории, форменной производной или итерационных сопряжённых решений.

| Сетка | Сумма четырёх компонент (65 цифр) | Разность binary64 − Decimal | Сумма − сохранённый итог из CSV |
|---|---:|---:|---:|
| W4B2 | 2.366510932953431774 | −4.01e−17 | +2.274e−15 |
| W5B2 | 2.366513234475434333 | +1.58e−16 | +2.033e−15 |
| W4B20 | 2.365926928024281158 | +6.81e−16 | −6.420e−16 |

Межсеточные разности из четырёх компонент:

| Переход | Δ сумма Decimal, м^-1 | Δ сумма double, м^-1 | Разность double − Decimal, м^-1 |
|---|---:|---:|---:|
| W4B2→W5B2 | +2.301522002559e−6 | +2.301522002756684e−6 | +1.9768e−16 |
| W4B2→W4B20 | −5.84004929150616e−4 | −5.84004929149895e−4 | +7.2101e−16 |

Для первого сравнения последняя ошибка округления порядка 10^-16 м^-1, то есть на ~10 порядков меньше наблюдаемой межсеточной разности ~2.3e−6 м^-1. Это **опровергает гипотезу, что сама последняя сумма 4 компонент является источником наблюдаемого различия**. Такой расчёт НЕ проверяет, не возникла ли значимая ошибка ранее при формировании каждой компоненты.

Дополнительный тест искусственного сокращения числа печатаемых *значащих* цифр каждой компоненты (сумма W5−W4): при 9 цифрах ошибка около 2.03%, при 10 — 0.123%, при 12 — 0.0010%, при 17 — ниже разрешения исходных строк. Для такого межсеточного сравнения 17-значный вывод достаточен; 6–8 цифр недостаточно.

## 3. Где остаётся риск округления/обусловленности

1. В P10V накопление `numerator`, `d_numerator`, `observed_volume` выполняется последовательно через `+=` по большому числу Q3-точек; при отмене крупных положительных/отрицательных вкладов возможно усиление ошибок суммирования. Нужно проверить `double` vs компенсированную сумму Neumaier/Kahan **на одних и тех же готовых точечных вкладах**, не меняя уравнения.
2. Для механического и теплового сопряжённых решателей накопление скалярных произведений и нормы зависит от double, а остаточная ошибка обусловлена ещё и качеством линейного решения. Для P10W измерены ненулевые алгебраические невязки; оценить их воздействие на градиент нужно через независимую проверку, а не по одному числу невязки.
3. На W4B2→W5B2 коэффициент компенсации **межсеточных приращений** отдельных компонент около 3215; это делает малый результат чувствительным к любым ошибкам самих компонент, независимо от причины (сетка, нелинейные решения, квадратура, конечная точность).
4. `double` не устраняет погрешности выбора ступенчатой B6-маски, квадратичной аппроксимации кривой поры и обусловленности матрицы. Достаточно точная арифметика не равна достаточно точному FEM-результату.
5. Полный переход на `long double`/quad потребует менять почти весь численный тракт, ввод/вывод, матрицы и сохранённые состояния: это **не** просто настройка компиляции. В зависимости от ABI удвоение памяти для скалярных полей и истории реально; сравнение с прежними `history.bin` может перестать работать. Приоритет у узконаправленного теста.

## 4. Какие данные действительно сохраняет P10N/P10W

Проверка `src/stage3d10p_partial_audit.cpp:102–175` и `src/stage3d10k_h0_coupled_pilot.cpp:143–148`:

- В `forward_history.bin` (либо явно заданном `--forward-cache FILE`) P10N сохраняет **каждый** `HistoryFrame`: `temperature` (nodal double), `repinned_u` (nodal double), `previous` (состояние EDV для каждой точки исходной Q3 квадратуры). Затем — финальное `u`, `qstate`, время и ранее вычисленные 3 функционала.
- Формат P10N version 1: 10 uint64 заголовка, 3 double функционалов, по каждому вектору контроль FNV. Заголовок проверяет mesh signature, числа узлов/тетраэдров/QP, dt, steps, cutoff и `sizeof(State)`; исходное чтение реализовано в `load_forward` и связано с **той же** сеткой.
- Файлы `restart.bin` и `adjoint_history/step_000006.bin` — сохранённые состояния `u` и EDV на отдельных шагах, но не обязательно содержат полные температурные и механические истории для 6 шагов. Их нельзя без проверки объявлять эквивалентом `forward_history.bin`.
- Достаточный P10N forward-cache даёт возможность пересчитать Q3-момент `jpeak` с *другим правилом маски* при **фиксированных тех же узловых полях** и Q3-состояниях, без нового глобального FEM-решения, при условии корректного согласования нормировки и временных весов.
- Для перехода от Q3 к Q4 нельзя просто взять Q3-значения `State` в новых точках: это разные материальные точки. Возможный отдельный контроль — локальное воспроизведение EDV-истории на новых Q4-точках **по сохранённой последовательности узловых u и T** без повторного глобального прямого решения. Требуется новая проверенная постобработка; это не прямое переиспользование Q3 history и результат не является полным Q4 FEM-расчётом.
- Код P10W при стандартном запуске P10N записывает `forward_history.bin` в каталог запуска, либо использует предоставленный `--reuse-forward`. Возможность восстановления фактически сохранённых кэшей на G:/F: пока не проверена.

## 5. Принятое исследовательское действие (не изменение модели)

**Рекомендация:** не переписывать EDV/Tet10 решатель под extended/quad precision, пока не проверены ошибки накопления и состояние прямой истории. Проводить арифметическое исследование строго на одной сетке, согласно P10AO.

Следующая дешёвая операция — чтение только 104-байтных заголовков кандидатов `forward_history.bin` / `history.bin` и метаданных контрольных точек на G: с помощью автономного пакета `Stage3D07_LIT07_PRECISION_HISTORY_INVENTORY_20261116.zip` (его `lit07_history_inventory.py` и `01_LIT07_HISTORY_INVENTORY.cmd`, проверены на синтетическом бинарном заголовке). SHA256 ZIP: `700922c35dbcd4b076ed35d6c3c9f8efd69410069337f5d7ce0790396deaedca`. Пользователь должен передать **только один небольшой CSV** `G:\ildar\Stage3D07\LOCAL_RUNS\LIT07_HISTORY_INVENTORY\LIT07_HISTORY_FILES.csv`. Самих многогигабайтных бинарных файлов не передавать.

После получения инвентаризации: выбирать **одну** сетку с сохранённой историей, затем делать проверку перерасчёта N_8 на той же Q3 истории при неизменной маске (обязательная parity), после чего альтернативную маску/интегрирование и только при необходимости компенсированную сумму. Цель — разделить ошибку выбора B6 от ошибки накопления и пространственной ошибки прямых полей, без нового сопряжённого FEM.
