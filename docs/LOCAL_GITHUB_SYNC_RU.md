# Stage3D07: как связаны локальный ПК, GitHub и PORE ONE CLICK

Актуализация: **18.11.2026**. Репозиторий GitHub: `galildmur-dotcom/stage3d07_ice_pore`.

## Три разных хранилища

1. **ПК `G:\ildar\Stage3D07`:** исходный код, локальные изменения и большие исходные FEM-расчёты. Состояние Git здесь независимо от состояния GitHub. По экспорту P10BF локальный `HEAD=c0498f6d...`, а пять файлов имели `M/??`; это не чистый снимок сборки.
2. **GitHub, `master`:** постоянная точка входа `START_NEW_CHAT.md`, а не автоматически самый новый научный код.
3. **GitHub, `research/p10bb-w5b2-20261118`:** актуальная доказательная ветка для P10AZ–P10BF, первичных CSV и исследовательских документов. Она может отличаться от локального `master` на ПК.

`git push` передаёт только закоммиченные изменения **конкретной ветки** на **указанный remote**. ZIP в чате и `Snapshot-For-ChatGPT.ps1` не выполняют `push`; загрузка файла в ChatGPT сама по себе не обновляет GitHub. `origin` может указывать на исторический GitFlic, поэтому наличие Git на ПК само по себе не удостоверяет связь с GitHub.

## До любого локального импорта или отправки

Выполнять в локальном `G:\ildar\Stage3D07` **только читающую** проверку (через Git Bash/терминал Git for Windows):

```powershell
git rev-parse HEAD
git branch --show-current
git remote -v
git status --short
git fetch --dry-run origin
```

Сверить адрес remote: если `origin` указывает на GitFlic, **не перенастраивать его автоматически и не запускать старую кнопку 1**, а согласовать отдельное безопасное подключение GitHub (например, новый remote `github`, не заменяя `origin` без решения владельца). История локальных коммитов и изменения файлов могут расходиться с веткой исследования; запрещены автоматические `reset --hard`, `clean`, force-push и слепое применение исторического патча.

## Что сохранять для следующего чата

После значимого запуска/публикации фиксировать: `run_id`; цель Qt Creator; дату; аргументы; имя сетки и её SHA-256; SHA-256 фактического EXE; Git HEAD на ПК; `git status --short`; состояние `origin`/ветки; SHA первичных CSV; что действительно проверено. Не заполнять отсутствующий SHA догадкой. Обновлять `docs/PROJECT_STATE.md` и `master/START_NEW_CHAT.md`, оставлять ссылку на конкретную рабочую ветку, не переписывая исторические `RUN_MANIFEST.json`.

**Важно:** исходник из чистого Git commit и совпадающий хеш `exe` — две разные части доказательной цепочки; без журнала сборки нельзя достоверно приписать EXE конкретный Git SHA.
