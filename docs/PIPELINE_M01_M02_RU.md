# M01/M02: паспорт расчёта и регистрация в реестре Stage3D07

Состояние на 2026-11-10. Этот документ описывает **внедрённые инфраструктурные функции**, а не окончательную физическую верификацию сопряжённого МКЭ-решателя.

## 1. Назначение и пути

- Код: `G:\ildar\Stage3D07` — Git, Qt Creator, CMake, MinGW Release.
- Большие результаты: `G:\ildar\Stage3D07\LOCAL_RUNS\<run_id>` — вне Git.
- Паспорт новых P10S: `G:\ildar\Stage3D07\LOCAL_RUNS\<run_id>\RUN_MANIFEST.json`.
- Единый индекс: `G:\ildar\Stage3D07\experiments\RUN_REGISTRY.csv` — небольшой текстовый файл в Git.
- Резервные копии: физически отдельный диск `F:`, по `docs/F_ARCHIVE_PLAN.md`. Факт регистрации **не означает**, что расчёт уже скопирован на F.

## 2. M01 — формирование RUN_MANIFEST.json

При новом запуске Stage3D10S программа записывает паспорт, включающий `run_id`, состояние, время, фактические аргументы, имя сетки, SHA-256 сетки и исполняемого файла, число шагов, модель материала, температурную модель, амплитуду изменения формы и выходные файлы.

| Статус паспорта | Смысл | Можно вносить в реестр? |
| --- | --- | --- |
| `preflight_ok` | Предварительная проверка, не полный расчёт | Нет |
| `completed` + `exit_code=0` + `preflight=false` | Программа завершила основной расчёт | Только после дополнительных проверок M02 |
| `failed_checks` или иной незавершённый/ошибочный | Часть проверок не пройдена или запуск не завершён | Нет |

Поле `code.git_commit_at_cmake_configure` фиксирует SHA на момент конфигурации CMake. Оно **не удостоверяет**, что рабочее дерево при компиляции было чистым. Для строгой воспроизводимости нужны запись состояния Git, SHA-256 exe и сетки и идентификация настроек сборки.

## 3. M02 — ручная регистрация завершённого расчёта

Цель `ice3d_register_manifest` не запускает FEM. Она принимает путь к паспорту и реестру и проверяет статус, код возврата, отсутствие `preflight`, совпадение `run_id` с каталогом, SHA-256 сетки, а также наличие **шести** CSV:

1. `P10N_DELTA_SCAN.csv`
2. `P10P_PARTIAL_COMPONENTS.csv`
3. `P10P_STEP_COMPONENTS.csv`
4. `P10S_PARTITION_AUDIT.csv`
5. `P10S_SHELL_SUMMARY.csv`
6. `P10S_STEP_SHELL_COMPONENTS.csv`

Утилита сохраняет формат `RUN_REGISTRY.csv` из 20 полей, не создаёт дубль `run_id`, использует временную `.lock` и `.pending` для защиты обновления. Регистрация производится **по отдельной команде**, не автоматически в конце P10S.

Для будущего завершённого расчёта `NEW_RUN`, после проверки существования его папки, в Qt Creator выбрать цель **`ice3d_register_manifest`**, набор **Desktop MinGW Release**, аргументы:

```text
--manifest G:/ildar/Stage3D07/LOCAL_RUNS/NEW_RUN/RUN_MANIFEST.json --registry G:/ildar/Stage3D07/experiments/RUN_REGISTRY.csv --dry-run
```

Ожидать `ICE3D_REGISTRY_DRY_RUN_OK`. Если проверка прошла и параметры научного эксперимента подтверждены, повторить те же аргументы **без** `--dry-run`. Ожидать `ICE3D_REGISTRY_ADDED`. Повторная регистрация того же `run_id` должна вернуть `ICE3D_REGISTRY_ALREADY_EXISTS` без дубля.

Затем посмотреть изменение **только реестра**:

```bash
git -C "G:/ildar/Stage3D07" diff -- experiments/RUN_REGISTRY.csv
```

Не выполнять эти действия для старого `P10S_H4W4B2_D2P5`: эксперимент исторический, его паспорт M01 во время расчёта не создавался, а запись уже добавлена вручную с отмеченными неизвестными полями.

## 4. Что испытано, а что нет

- **M01:** на Windows Qt Creator проверены автономный тест и H0 preflight. Паспорт H0 имеет `status=preflight_ok`, `exit_code=0`; список выходных CSV пуст. Это правильный результат предварительного режима.
- **M02:** на Windows Qt Creator получен `ICE3D_REGISTRY_UNIT_OK`; тест с H0 выдал `ICE3D_REGISTRY_SKIPPED_PREFLIGHT (registry unchanged)`.
- **Не испытано на Windows в реальном полном расчёте:** полный цикл новый P10S → `status=completed` → `--dry-run` → запись CSV → проверка привязки к конкретному исходному состоянию и архивной копии.
- **Не доказано этим этапом:** независимая правильность adjoint-градиентов, пространственная и временная сходимость, научная достоверность функционалов. В текущем коде `jen` не следует без обоснования называть `j_safety`.

## 5. Подготовка следующей контрольной точки

После завершения действующих организационных правок:

1. Получить `git status --short` и `git rev-parse HEAD`.
2. Сделать коммит только проверенных документов/кода (не добавляя случайно большие каталоги `LOCAL_RUNS`).
3. `git push origin master` и проверить результат.
4. Сохранить на F полный `git bundle` уже **нового** HEAD и выполнить `git bundle verify`.

Уже проверенный `Stage3D07_9e79fcb_20261110.bundle` остаётся самостоятельной восстановимой копией истории на тот момент; он не содержит последующие изменения.
