# F_ARCHIVE_PLAN — архивирование Stage3D07 на диске F

Версия: 2026-11-10. `F:` — заявленные пользователем 2 ТБ. Считаем F **местом архивных копий**, а не второй рабочей сборкой проекта. Исходный код и программа остаются на `G:`.

## 1. Папки — создать вручную в Проводнике Windows

| Путь на F | Что хранить | Когда обновлять | Кто решает |
| --- | --- | --- | --- |
| `F:\ICE_PORE_3D_ARCHIVE\01_GIT_BUNDLES` | Самодостаточные Git bundle всех веток/тегов | После важных коммитов и хотя бы еженедельно | Пользователь по командам ассистента |
| `F:\ICE_PORE_3D_ARCHIVE\02_RUNS_A` | Незаменимые или ключевые дорогие расчёты целиком, вместе с доступными журналами | По завершении проверенного расчёта | Вместе определяем категорию A |
| `F:\ICE_PORE_3D_ARCHIVE\03_RUNS_B` | Дорогие, но воспроизводимые запуски | По мере свободного места | Вместе определяем категорию B |
| `F:\ICE_PORE_3D_ARCHIVE\04_MESHES` | Уникальные крупные `.msh` и паспорта генерации | После проверки сетки | Вместе |
| `F:\ICE_PORE_3D_ARCHIVE\05_ACTIVE_CHECKPOINTS` | Отдельные согласованные копии `restart.bin` незавершённых многосуточных расчётов | Только при безопасной точке сохранения, не посреди записи | Пользователь |
| `F:\ICE_PORE_3D_ARCHIVE\06_ARTICLE_RELEASES` | Отправленные версии статьи, рисунков, приложения | При значимых редакциях и отправке | Вместе |
| `F:\ICE_PORE_3D_ARCHIVE\99_CATALOG` | Реестр архивов, хеши, список того, что существует только на G | При каждом архивировании | Ассистент готовит формат, пользователь записывает факт |

Стартовый шаблон реестра: `archive_templates/ARCHIVE_CATALOG.csv` внутри пакета. После создания папки F скопировать его в `F:\ICE_PORE_3D_ARCHIVE\99_CATALOG\ARCHIVE_CATALOG.csv`.

Каждая папка возникает **на F при первом её использовании**. Не следует копировать туда вторую папку `build` или временные сборочные файлы. Не дублировать одни и те же `restart.bin` одновременно в `02_RUNS_A` и `05_ACTIVE_CHECKPOINTS` без причины.

## 2. Что проверить до массового копирования

1. В Windows открыть `Win + R` → `diskmgmt.msc` и посмотреть номера физических дисков для томов `F:` и `G:`. Разные буквы могут относиться к одному устройству. Если оба тома на одном физическом диске, архив F защищает от случайного удаления файлов, но **не** от поломки этого диска.
2. В Git Bash выполнить:

   ```bash
   df -h /f /g
   du -sh /g/ildar/Stage3D07/LOCAL_RUNS /g/ildar/Stage3D07/LOCAL_RUNS_OPTIMIZED /g/ildar/Stage3D07/meshes /g/ildar/Stage3D07/P10M_MESHES 2>/dev/null
   ```

3. Если `du` не видит какую-либо папку, прислать список реально существующих. Сообщить также, где лежат основные результаты на диске G вне `Stage3D07`.

## 3. Независимый архив Git

Сначала создать `01_GIT_BUNDLES` в Проводнике. В Git Bash выполнить:

```bash
git -C "G:/ildar/Stage3D07" status --short
git -C "G:/ildar/Stage3D07" bundle create "F:/ICE_PORE_3D_ARCHIVE/01_GIT_BUNDLES/Stage3D07_2026-11-10.bundle" --all
git -C "G:/ildar/Stage3D07" bundle verify "F:/ICE_PORE_3D_ARCHIVE/01_GIT_BUNDLES/Stage3D07_2026-11-10.bundle"
```

Наличие незакоммиченных файлов в `status --short` не препятствует созданию bundle, но они в архив **не попадут**. Поэтому перед важной копией сначала проверять, что нужные изменения закоммичены и отправлены. Имя архивного файла должно быть уникальным; архивы за разные даты не перезаписывать.

## 4. Копирование большой завершённой кампании

Пока нет точного пути запуска, **не применять массовое копирование всего** `LOCAL_RUNS` и не запускать зеркалирование.

1. Отобрать конкретную папку законченного запуска, например `<фактическая папка P10N>` — выясним по реальному дереву.
2. Убедиться, что программа больше не пишет в эту папку. Если расчёт идёт, копировать только уже закрытый checkpoint после предусмотренного в программе безопасного сохранения.
3. Копировать в `F:\ICE_PORE_3D_ARCHIVE\02_RUNS_A\<run_id>` через Проводник или командой `robocopy` с точными путями. Для `robocopy` использовать `/E /Z /R:2 /W:5 /COPY:DAT /DCOPY:DAT /XJ`; **не использовать** `/MIR`, `/PURGE` или `/MOVE`.
4. Сравнить количество файлов/объём и для важных бинарных файлов проверить SHA-256 по обеим копиям. Для Windows пример одной пары файлов: `certutil -hashfile "G:\...\restart.bin" SHA256` и `certutil -hashfile "F:\...\restart.bin" SHA256`.
5. Записать в `99_CATALOG` фактический исходный путь, целевой путь, дату, размер, результат проверки и статус `A/B`; после этого добавить запись в реестр проекта на G.

Никаких исходных данных на G **не удалять** после копирования без отдельной явной проверки и решения исследователя. Со временем потребление места на F следует контролировать, а срок хранения устанавливать по научной ценности, не по одной лишь давности.

## 5. Фиксация полноты архива

Архив готов только если: исходный запуск идентифицирован; известен status завершения; код/входные данные связаны с Git SHA, если он достоверно известен; файл на F доступен для чтения; есть фактическая запись в каталоге; сохранён минимальный независимый протокол проверки.

**Ограничение:** GitFlic + локальный Git + F на том же физическом накопителе не являются тремя независимыми копиями расчётных данных. Внешний диск или удалённое архивное хранение по-прежнему желательны для незаменимой категории A.
